## Authoritative docs — read these first

This repo's operating knowledge lives in two hand-maintained Korean documents, not in code comments. Read them before any non-trivial change:

- **[전파정책AI_지침_운영핵심.md](전파정책AI_지침_운영핵심.md)** — operational core: system structure, full DB schema, pg_cron schedule, the "must-check" runbook, and a ~280-item **"하지 말아야 할 것"(do-not) guardrail list** (newest first). Every entry is a scar from a real incident. How to read it (2026-09-24, the file is ~1,560 lines): **structural changes** (new script/workflow/schedule/table/notification path, flow change) → read the whole do-not section; **small fixes** (one-line bug, wording, a constant) → grep it for the names you touch (table/script/function/key) **and** read the newest ~40 entries at its top. **When unsure which kind it is, read the whole section.**
- **[전파정책AI_배경역사.md](전파정책AI_배경역사.md)** — background/history: the detailed why behind each guardrail, past-incident postmortems (#15–#19), dates, commit hashes.
- **[HANDOFF.md](HANDOFF.md)** — account-handoff procedure (multiple people share this same PC/folder under one Windows account).

**Doc-update rule (from the guidelines):** when you add a crawler/script/workflow, change scheduling, change a Supabase table, change a notification channel, change system flow, or discover a new constraint → update *both* the 지침 (rule + one-line reason) and the 배경역사 (detailed account), and provide the full updated text of both. Pure bugfixes with no behavior change are exempt.

## What this is

SKT Comm Center 기술정책팀's radio/telecom **policy-monitoring automation system**, run by a single operator. Crawlers gather government notices, laws, national-assembly bills, and news into Supabase; a morning briefing goes out daily; a GitHub Pages dashboard offers RAG-based AI advisory and report-draft generation.

- Dashboard: **https://radio-policy.github.io/ (GitHub Pages — canonical, all notification links point here)** · backup https://radio-policy.gitlab.io/
  - GitHub Pages gzips and serves from a Fastly edge in Incheon; GitLab Pages serves everything uncompressed. Measured 2026-09-15: `app.js` 216KB/0.19s vs 718KB/2.68s. GitLab was canonical only while the GitHub account was flagged (2026-08-01~08-25, #109); it stays deployed as the backup site. **The git topology is unchanged — GitLab is still the primary repo, GitHub the mirror, and every push goes to both.**

**Session model + effort rule (operator rule, 2026-09-24/25; memory `tell-when-fable-needed`):** state in one line the **(model, effort) pair** the item needs — at three moments, never skipped: ① the first reply of a session (for the item the operator opened with), ② **every time an item is finished, before starting the next one** (the last paragraph of the completion report names the next item and its pair), ③ whenever the operator adds an item mid-session. Fixed shape: `▶ 다음 항목 「<항목>」: (<모델>, <노력>) — 현재 짝 (<모델>, <노력>)과 같음 → 이 세션에서 계속 / 다름 → 지금 새 세션으로 전환 또는 모아서 나중에 (이유 한 줄) · 새 세션/compact 권고`. If the current session's own pair is wrong for the work it is doing (e.g. a Fable session doing procedural work), say so once and recommend where the remaining quota should go instead.

**Model by work type.** Procedural work (a procedure already written in the docs, single-file bug fixes, measurements, handoff notes) → Opus 5.5; judgment-heavy work (structural design across files or across the two editions, do-not rule revisions, team-level AI judging structures, search ranking / regression-set design, live-DB anomalies that need root-causing, flow changes that get a 배경역사 number) → Fable 5.1. The Fable quota is spent only on Fable-type work — never on procedural work — and Fable-type work is **not** moved to Opus while Fable is available (operator clarification 2026-09-25: the goal is "Fable-type work on Fable, Opus-type work on Opus; when Fable runs out, push Opus as far as it goes", not a blanket replacement).

**Effort by activity (independent of model):** design drafts / research / decision tables → high (research-type curves are flat above that); implementation / debugging / regression / deploy → xhigh (the Claude Code default); judging-rubric counter-example review, guardrail / flow hole checks and root-cause tracing → max. Each level is where that activity's measured quality curve plateaus — raising it further adds cost, not quality — so none of these pairs trades quality for quota (operator confirmation 2026-09-25). Pairs in normal use: **(Opus 5.5, high)** procedural prep; **(Opus 5.5, xhigh)** procedural implementation; **(Fable 5.1, high)** a Fable-type design/decision session (the default Fable pair, spends the quota slowest); **(Fable 5.1, xhigh)** a Fable-type item whose session also implements and regression-tests it in one go (the §5-2 B-series shape — do not split design and implementation into two sessions just to change effort, the switch costs more); **(Fable 5.1, max)** rubric counter-example review, guardrail / flow hole checks and root-causing. (Opus 5.5, max) is not used while Fable is available. **Switching either the model or the effort costs the same** (mid-session = full cache rewrite; new session = ≈75–80K fixed context reload + memory/지침 re-read), so batch items by pair, with an asymmetric rule (operator decision 2026-09-25): ① **the current pair is higher than the item needs** (a short question, or 1–2 short items) → do not step down, do it on the current pair (a higher pair always covers a lower one; the few K tokens cost less than any window); ② **the current pair is lower and one short judgment is needed** → keep this session on its pair and open a **separate throw-away window on the needed pair** with a self-contained question (paste the decision table / code excerpt it needs), bring back only the answer; that window reads and answers, it never edits or commits (one committing session); a pure-judgment question that needs no repo context can be opened outside the project folder so it does not load CLAUDE.md and memory; ③ **the current pair is lower and 3+ work items (or a continuing design) need the other pair** → leave a record (progress in the memory file, a commit, a one-line start phrase) and open a new session on that pair. A Fable session with a run of Opus-type items is case ③, not case ①. **Never change the model or the effort inside the running window**: it re-sends the whole conversation uncached; the only exception is a conversation still shorter than the fixed context (≈75–80K, i.e. just started), where switching in place is the cheaper of the two. Also say whether a new session or `/compact` is the better next step (new session when the work unit or pair changes, after a >1h gap, or past ≈200K context; compact when the same unit continues and its decisions/numbers are still needed).

**When the Fable quota is exhausted** (operator decision 2026-09-25: proceed, do not wait for the reset — speed first): every Fable-type item runs immediately on Opus 5.5 with **xhigh as the floor** — design / decision sessions and design + implementation + regression sessions → **(Opus 5.5, xhigh)**; rubric counter-example review, guardrail / flow hole checks and root-cause tracing → **(Opus 5.5, max)**; a design document that contains a judging-rubric section → the whole document in one **(Opus 5.5, max)** session (never split to change effort). Not high: a substitute session almost always continues into implementation, where high already loses measured quality, and the design part is too short for high to save anything. Not max across the board: above xhigh only the reasoning-ceiling activities gain measurably; elsewhere it only costs 1.5–3× per turn. Procedural items keep their Opus pairs unchanged. Every such result carries a **`Fable 재검토`** mark in three places (the design doc, the memory progress file and the commit message) so the first Fable session after the reset finds it. The single hold is a backfill or bulk judging run — expensive to redo — which waits for the Fable rubric re-review. Re-review pairs after the reset (a review, not a redo):

| Work done on Opus 5.5 in Fable's place | Fable re-review pair | What the re-review does |
|---|---|---|
| (Opus 5.5, xhigh) design / decision document, no judging-rubric section | **(Fable 5.1, high)** | Reads the draft — structure, decision table, do-not conflicts, both-edition impact — fixes and approves. |
| (Opus 5.5, max) design / decision document **with** a judging-rubric section | **(Fable 5.1, max)**, one session for the whole document (never a high session plus a max session) | Rubric section: counter-examples, scale, evidence-citation rules; the rest as above. |
| (Opus 5.5, xhigh) design + implementation + regression of a Fable-type item (B-series shape, queue / Edge / flow / guardrail parts included) | **(Fable 5.1, xhigh)** | Design + code + regression set in one pass. A design flaw becomes a new Fable item. |
| (Opus 5.5, max) rubric counter-example review or root-cause | **(Fable 5.1, max)** | Re-checks the conclusion against its evidence — keep or overturn. An overturn spawns a fix item under the normal rules. |

Order after the reset: all pending `Fable 재검토` items first, batched by pair — the max batch first (an overturned conclusion has the widest blast radius), then xhigh, then high — and new Fable work only after that.
