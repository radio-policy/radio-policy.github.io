## 2. 층(layer) 정의와 결정 규칙

등급 순서: 참고(0) < 보통(1) < 긴급(2).

```
                 ┌ 사람 수정(팀)  ─ 그대로 (공통 규칙 하한도 뚫을 수 있음)
 팀 T의 값  =    ├ 팀 규칙 set    ─ 그 값 (팀 AI 생략)
                 ├ 팀 규칙 min    ─ 하한만 건다 → 팀 AI는 돈다
                 ├ 팀 AI          ─ max(팀 AI, 팀 min 하한, 공통 min 하한)   ← 공통 set 적중이면 생략
                 └ (팀 지침 없음) ─ 공통값
 공통값      =   ┌ 관리자 수정(공통) ─ 그대로
                 ├ 공통 규칙 set  ─ 그 값 (공통 AI 생략)                      ← 적중 id 기록
                 ├ 공통 규칙 min  ─ 하한만 → 공통 AI는 돈다, 결과 = max(AI, 하한) ← 적중 id 기록(값 불변이라도)
                 └ 공통 AI        ─ classify_urgency
```

**적중과 AI 재판정의 관계(2026-09-25 사내 회신 2로 정리, 운영자 결정 D9)** — 요청문 원칙 6("걸린 기사는 판정 대상에서 뺀다")을 다음과 같이 좁힌다:
- **min 적중 → 그 층 AI를 돌린다.** 결과 = max(AI 값, 하한). 뒤집기는 하한이 막는다(원래 긴급인 주파수 기사를 AI가 참고로 내린 사내 사고는 하한만으로 막힌다). `urgency_rule`은 적중 기록으로 그대로 남긴다.
- **set 적중 → 그 층과 그 아래 층 AI를 건너뛴다**(set은 운영자가 등급을 못 박은 것). 공통 set에 동의하지 않는 팀은 팀 규칙(set)이나 사내 「다르게/끄기」로 뺀다 → 그 팀 AI가 다시 돈다.
- **하한은 위 층에도 걸린다**: 공통 min 하한 아래로 팀 AI도 못 내린다. 팀 규칙 set과 사람 수정만 내릴 수 있다.
- 이유: 5번 규칙(부처+통신)처럼 넓게 걸리는 min 규칙까지 AI를 빼면 팀 AI가 도는 범위가 23% 줄어든다. 사내 팀 AI는 이미 이 방식(공통 적중 기사도 판정, 9/25부터 하한 적용)이고, 사내 공통 AI만 「공통 set 적중만 생략」으로 맞출 예정.

- **공통 규칙은 팀 설정이 없어도 전원에게 적용된다(2026-09-25 운영자 지시).** 1단계는 팀 층이 없으므로 공통 규칙 결과가 곧 모든 이용자·알림·브리핑이 보는 값이다. 2단계 뒤에도 팀 지침·팀 규칙·팀 값이 없는 이용자(비로그인·팀 미지정·지침 없는 팀)는 공통 규칙이 적용된 공통값을 그대로 본다. 팀 설정은 공통값 위에 덧씌우는 것이고, 공통 규칙을 끄는 방법은 그 팀의 set 규칙 또는 사람 수정뿐이다.
- **min은 올리기만, set은 지정.** 올리려던 규칙이 AI의 더 높은 등급을 끌어내리지 않는다.
- **처음 걸린 규칙 하나가 정한다.** 배열 순서 = 우선순위. 강한 규칙을 앞에.
- **「걸렸다」와 「값이 바뀌었다」를 구분한다.** 걸린 기사는 `urgency_rule`(규칙 id)에 값이 안 바뀌어도 남긴다(출처 표시·통계·사내 정본). AI 생략은 set 적중에만(위 D9).
- **규칙은 제목 + 네이버 요약만 본다.** 본문은 보지 않는다(과거 사례 언급 오탐).
- **화면과 알림은 같은 저장값**을 쓴다(1단계). 2단계 팀 덧씌우기도 함수 하나(`effectiveUrgency`)로 통일하고 배포 전 전체 기사로 대조한다.
- **어느 층에서 온 값인지 화면에 표시**한다: `AI 판정` / `규칙: <note>` / `담당자 수정` (+ 2단계: `팀 규칙`·`팀 AI`·`팀 담당자`).

## 3. 규칙 형식 (데이터, 표 `urgency_rules` — 2026-09-25 운영자 회신으로 app_config 키에서 표로 변경)

저장은 **표 한 개**, 행 하나가 규칙 하나다. 팀 칸(`team_id`, null = 공통)을 1단계부터 둔다 — 팀장이 자기 팀 규칙만 고치는 DB 정책은 키 한 줄(app_config)로는 못 건다.

```sql
create table public.urgency_rules (
  id          text primary key,                  -- 'skt_gukgam_witness'
  team_id     smallint references public.teams(id),   -- null = 공통
  position    int  not null default 100,         -- 작을수록 먼저 (배열 순서 대신)
  mode        text not null check (mode in ('min','set')),
  level       text not null check (level in ('긴급','보통','참고')),
  any_words   jsonb not null,                    -- ["SK텔레콤", …]
  and_any     jsonb not null default '[]',       -- [["국감","국정감사"],["증인",…]]  (평면 배열도 허용)
  none_words  jsonb not null default '[]',
  note        text not null default '',
  enabled     boolean not null default true,
  updated_by  uuid, updated_at timestamptz not null default now()
);
-- RLS: SELECT anon·authenticated — 공통·팀·enabled=false 모두(조건 없음). 낱말 목록이라 비밀 아님. 사내 다리가 anon 키로
--      공통 행을 enabled 무관하게 전부 받아 「원본 삭제됨」 표시에 쓴다(사내 회신 2) — anon SELECT에 enabled=true 조건을 넣지 말 것
--      INSERT/UPDATE/DELETE authenticated: 공통(team_id is null) → is_admin() / 팀 → is_admin() or (is_leader() and team_id = my_team())
--      service_role: 전권(크롤러 읽기). GRANT 3역할 명시(#214). 시퀀스 없음.
```

규칙 한 줄을 JSON으로 보면(편집기·크롤러가 다루는 모양):

```json
[
  {
    "id": "skt_gukgam_witness",
    "min": "긴급",
    "any": ["SK텔레콤", "SKT", "통신3사", "이통3사", "통신 3사", "이통 3사", "이동통신 3사"],
    "and_any": [
      ["국감", "국정감사"],
      ["증인", "참고인", "소환", "출석", "국감행", "국감장"]
    ],
    "none": [],
    "note": "국정감사 증인·참고인 채택·소환·출석 — 전 팀 공통 긴급 (2026-09-25 운영자 규칙)"
  }
]
```

- 판정: `any` 중 하나 이상 **AND** `and_any`의 **각 그룹**마다 하나 이상 **AND** `none` 없음. `and_any`는 평면 배열도 허용(그룹 하나로 해석) — 요청안 형식과 호환.
- `min` 또는 `set` 중 하나. `id`는 표시·집합 관리용(필수). `note`는 화면에 그대로 보인다.
- 매칭은 부분 문자열(한국어 단어 경계 없음). do-not #99(`AI`→`KAIST` 오탐)와 같은 함정이 있으니 **규칙을 넣기 전에 최근 30일 기사에 돌려 오탐을 본다**(1-3처럼). 2~3자 낱말(`증인`·`소환`)은 반드시 다른 그룹과 AND로만 쓴다.
- 코드에 같은 규칙을 **FALLBACK 상수**로도 둔다 — 표 조회 실패 시 비상용(#53 「DB가 원본, 코드는 폴백」과 같은 구조).

**매처 계약(사내판 회신 반영, 두 판 공통)**
- 입력 텍스트 = `NFC 정규화(제목 + " " + 요약)`. 사내 파일은 맥·윈도를 오가 NFD가 섞인다 — 외부 매처도 같은 정규화를 넣는다.
- 반환 = `(등급, 걸린 규칙 id 또는 None, 값 변경 여부 bool)` 셋. 사내 세 지점(적재 색인·화면 계산·알림 계산)이 모두 쓴다.
- **첫 적중 규칙이 정한다** = 첫 적중이 min이고 이미 그 이상이면 **값 그대로, 뒤 규칙으로 넘어가지 않음**(사내 현행). 케이스 파일에 못 박는다.
- 적중 기록(`urgency_rule`)은 **값이 바뀌지 않아도** 남긴다 — 사내가 「공통 규칙이 답한 기사」 표시로 써서 팀 AI가 뒤집지 못하게 막는다(사내 실제 사고: 원래 긴급인 주파수 기사를 min 규칙이 그대로 두자 팀 AI가 참고로 내림).
- 규칙 `id`는 **영구 불변**(이름을 바꿔도 id 유지, 지운 id 재사용 금지) — 사내 팀 사본이 id로 원본을 가리킨다. 편집기는 id를 만들 때 자동 생성(`slug_YYMMDD`)하고 수정 화면에서 id 칸은 잠근다.
- 삭제는 **`enabled=false`만, 행 삭제 없음**(사내가 공통 행을 통째로 받아 비교하므로 한 가지로 고정). 행마다 `updated_at`(있음) — 사내 「다르게」 사본이 원본 변경을 알아채는 기준.
- `team_id`는 매처가 보지 않는다. 케이스 파일(`tests/fixtures/urgency_rules_cases.json`)에도 넣지 않는다.
- 끄기·팀 사본 치환은 **목록을 만드는 쪽**(외부: 로더 / 사내: 상속 편집기)이 하고 매처는 받은 목록을 순서대로 돌기만 한다 — `position`은 치환 뒤에도 유지(첫 적중이 정하므로 자리가 바뀌면 안 된다).

## 4. 1단계 — 공통 규칙 층 (먼저, 작게)

### 4-1. 크롤러 (`crawler.py`)

1. `load_urgency_rules()` — `load_news_criteria()`(1128행)와 같은 try/except·폴백 패턴: 표 `urgency_rules`에서 `enabled` 행을 `position` 순으로 읽고(1단계는 `team_id is null`만) 형식 검증(id·mode/level·any 필수, 등급값 셋 중 하나) → 실패·빈 값이면 `URGENCY_RULES_FALLBACK`. 실행당 1회. 로드 결과를 `[규칙] N개 로드(db|fallback)`로 로그.

   ```python
   hit = match_urgency_rules(_RULES, item['title'], _URGENCY_SUMMARY.get(url, ''))   # (rule_id, mode, level) or None
   if hit and hit.mode == 'set':
   ```

5. 알림·큐·브리핑은 저장값을 쓰므로 **코드 변경 없이 따라온다.** 재알림 억제(#44)도 그대로 거친다(같은 소환 보도 9건이 1건 + 리마인드로 나가는 현행 동작이 맞다).
6. `_URGENCY_CRITERIA` 즉시대응 목록에 같은 뜻의 항목 추가(낱말이 안 걸리는 변형 대비). 위치는 **「침해사고·장애·유출」 항목 바로 뒤, 「제도가 실제로 움직인 것」 앞** — 첫 항목은 사고 축이어야 하고(#161-보론4), 우선 규칙은 앞쪽에(#107):
   > - **국정감사에 SK텔레콤이(또는 통신3사가 일괄로) 증인·참고인으로 채택·신청·소환·출석하는 보도** — 채택 단계든 출석 당일이든 즉시대응. 타사만 소환된 국감 기사는 이 항목이 아니다(다른 항목으로 판단).
   기준문이 바뀌면 캐시 접두가 1회 재작성된다(1시간 캐시, 비용 미미). do-not(#161-보론2)에 따라 **`importance_feedback` 53건을 세션에서 재채점해 일치율 확인**(API 0회).

- **규칙 편집기(D4, 권고 포함·작게)**: 설정 탭의 「수집 키워드 관리」 카드(`app.js:7379-7479`)와 같은 구조로 「긴급도 규칙」 카드 — 위에 **「공통 / 내 팀」 선택**, 규칙 목록(행 단위 추가·수정·순서·켬끔) + 형식 검증 + **「최근 기사에 적용해 보기」**(같은 매처를 JS로 두고 `newsDataCache` 제목+요약에 돌려 적중 목록·값 변경 건수를 저장 전에 보여준다) + 저장. 화면 게이트는 안내용이고 관문은 RLS다(관리자 = 공통+모든 팀, 팀장 = 자기 팀, 팀원 = 열람). **1단계에서는 「내 팀」 탭을 회색으로 두고 "팀별 등급 저장이 열리면 사용"이라 적는다** — 저장은 되지만 적용될 자리가 없어 "고쳤는데 변화가 없다"는 오해를 막기 위함. 2단계 ②·④와 같은 회차에 켠다. 매처 JS는 Python `apply_urgency_rules`와 **같은 규칙**이어야 하며 단위 테스트의 6개 제목을 양쪽에서 돈다.

## 8. 사내판 — 팀별 규칙 편집기를 사내 콘솔에도 둔다 (2026-09-25 운영자 결정)

사내판은 DB 없이 JSONL 파일 위에서 이미 같은 5층 규칙 구조를 돌린다(§1-6). `news_grade.py`는 AI 호출 대상만 고르고(규칙 적중분 제외), 규칙 적용은 콘솔 적재 색인·콘솔 화면 계산·알림 앱 계산 세 곳이며 셋 다 매처 하나로 바꾼다. 사내 콘솔(`rp-console`)의 편집기는 **공통 규칙을 「같게/다르게」로 상속**한다(같게 = 외부 원본 추종, 다르게 = 그 팀만 수정·끔 + 원본 변경 시 「원본이 바뀜」 표시). **원칙은 "규칙 하나에 주인 하나"**:

| 규칙 | 주인(편집하는 곳) | 사내판에서의 취급 |
|---|---|---|
| 공통 규칙(team_id null) | 외부 대시보드 관리자 | 다리(`export_news.py`, anon 키 REST)가 `urgency_rules`의 공통 행을 받아 사내 표에 **읽기 전용**으로 둔다. 사내 `news_grade.py`가 공통 AI 판정 뒤에 적용 |
| 사내 팀 규칙 | 사내 콘솔의 그 팀 편집기(같은 형식의 JSONL, 주인 키 = 조직 코드 문자열, 팀장 = 운영자 명부) | 사내 팀 등급에만 적용. **외부로 올라가지 않는다** — 외부 규칙을 사내에서 고치려면 사내 앱에 쓰기 자격을 두거나 anon 쓰기를 열어야 하는데 둘 다 금지(#169-보론2·9/21 서비스 키 원칙), 흐름은 외부→사내 한 방향 유지 |
| 외부 팀 규칙(2단계 ⑦) | 외부 대시보드 팀장 | 사내판은 받지 않는다(외부 팀과 사내 조직이 1:1이 아님) |

조건 셋(어기면 같은 규칙이 두 판에서 다른 답을 낸다):
1. **형식·매처 동일** — §4-4의 `urgency_rules.py`/`urgency_rules.js`와 `tests/fixtures/urgency_rules_cases.json`을 그대로 이식하고 사내에서도 그 케이스 파일로 검증한다.
2. **공통 규칙은 외부 정본, 사내는 받아 읽기만** — 사내 편집기에서 공통 행은 회색(열람)으로 보이고 "외부 대시보드에서 관리"라고 적는다.
3. **적중 기록·출처 표시도 같이** — 사내 등급에도 `urgency_rule`(공통 규칙 id) / 팀 규칙 id를 남기고 콘솔 배지 옆에 `AI / 규칙: note / 담당자`를 보인다(#180 원칙 "판정은 한 곳에서, 사내는 옮기기만"은 **알림 대표 판정**에 관한 것이고 등급 판정은 이미 사내가 따로 하므로 충돌 없음 — 다만 공통 규칙을 사내가 따로 만들지 않는 것으로 그 취지를 지킨다).

그 밖의 영향:
- 1단계 외부 `news_feed.urgency` 저장값 변화는 스냅샷·다리로 **자동 반영**(사내 작업 없음). 새 컬럼 `urgency_rule`은 다리가 옮기면 출처 표시에 쓰고, 안 옮기면 무해. TOKTOK 알림은 `alert_suppress_log`만 보므로 무관.
