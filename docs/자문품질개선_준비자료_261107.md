## 9. 동시 호출

### 9-1. 지금 한 자문 안의 Anthropic 동시 호출

| 단계 | 호출 | 방식 | 코드 |
|---|---|---|---|
| 질문 확장 | Haiku 4.5 1회 | DB·Voyage 검색과 겹쳐 돔. Anthropic 호출끼리는 동시 아님 | `rag.ts:1434` |
| 답 생성 | Sonnet 5 1회 | **단독** — 앞 단계가 끝나야 시작 | `rag.ts:1669` |
| 인용 1차 | Haiku 4.5 묶음 1회 | 2차와 `Promise.all` | `cite_verify.js:2948` |
| 인용 2차 | Opus 5.5 항목당 1회 | 일꾼 6개, 실패 1회 재시도 | `cite_verify.js:2413-2429` |
| 다른 판 재판정 | 1·2차 다시 | 위 뒤에 순서대로, 안에서는 동시 | `cite_verify.js:2987` |

- 인용 항목별 호출은 **순서가 아니라 동시**다. 한 자문의 최대 동시 호출은 7개(Haiku 1 + Opus 6)다.
- 답 생성은 어떤 Anthropic 호출과도 겹치지 않는다.
- 대시보드는 답 스트림이 끝난 뒤 브라우저가 `verify-citations`를 부른다. 시간 상한 코드는 없다(§5-2).

### 9-2. 한도

**Anthropic** (https://platform.claude.com/docs/en/api/rate-limits, 2026-11-06 조회):

- 한도는 **조직 단위**이고 RPM·ITPM·OTPM으로 잰다. **동시 요청 수 한도는 문서에 항목이 없다.** 다만 RPM이 짧은 구간으로 나뉘어 적용될 수 있고(60 RPM → 초당 1), 급증 제한(acceleration limits)이 따로 있다.
- 캐시 읽기는 ITPM에 안 세고, 캐시 쓰기는 센다.

| 등급 | 월 지출 상한 | Sonnet 5 | Opus 5.5 | Haiku 4.5 | Haiku 5.5 |
|---|---|---|---|---|---|
| Start | $500 | 1,000 RPM | 4,000 RPM | 1,000 RPM | 4,000 RPM |
| Build | $1,000 | 5,000 RPM | 10,000 RPM | 5,000 RPM | 10,000 RPM |

- Start는 위 넷 모두 ITPM 2,000,000·OTPM 400,000이다(Fable은 다름). Build는 5,000,000·1,000,000이다.
- **외부 키의 실제 등급은 재지 않았다.** 10-11 화면 기록에 「티어 한도 $500/월」이 있어 Start로 추정한다. 확인은 Console의 Rate limits 화면이거나, 응답 머리글 `anthropic-ratelimit-*`(호출이 들어 **승인 뒤 측정**)다.
- 어림: 한 자문이 입력 60K·동시 4호출이면 ≈240K ITPM이다. Start 2M의 12 %이고 월 42건이면 RPM·TPM은 제약이 아니다. 같은 분에 10명이 몰려도 비캐시 ≈2.4M으로 경계에 닿는다. 그때는 429 + `retry-after`를 처리해야 한다. 지금 `callSonnet`에는 429 재시도가 없고, 실패하면 오류로 끝난다(`rag.ts:396`).
- **더 가까운 제약은 지출 한도다.** 10-11 기록에 Console 월 지출 한도 $150, 10월 사용 $81.23이 있다. 프로필 C(월 +$32~42)면 경계에 근접한다. 자기 지출 한도에 닿으면 HTTP 400으로 **같은 조직의 크롤러 판정까지 멈춘다**. 현재 한도와 크레딧 금액은 다시 확인해야 한다(기억 파일 기록이 시기별로 엇갈린다).

**Edge:** 벽시계 400초, 응답 전 유휴 150초, CPU 2초(§5-1). 응답 뒤 백그라운드 전용 한도는 문서에 없다.

- 「400초 초과」는 한 Edge 실행에 전부 담을 때다. 대시보드처럼 브라우저가 호출별로 부르면 호출당 400초라 이 값은 적용되지 않는다.
- 대시보드는 답 호출 자체가 길다. 동시 호출로 줄이기 전에 effort·출력 길이를 `/ask`처럼 맞추면 가장 크게 줄 수 있다. 다만 #281 측정이 있어 재측정 없이 바꾸면 안 된다.

**비동기 꼴**(먼저 접수·초안을 보이고 뒤에서 완성): 총 시간은 위 동기+동시와 같고 사용자가 보는 시점만 앞당겨진다.

| 시점 | `/ask` 중앙 / p90 | 대시보드 중앙 / p90 |
|---|---|---|
| 초안 첫 글자(스트리밍) | 15 / 16초 | 15 / 16초 |
| 초안 끝 | 42 / 56초 | 99 / 147초 |
| 보강까지 끝 | 68 / 84초 | 152 / 205초 |

- 텔레그램 `/ask`는 **이미 비동기 틀**이다(웹훅 200 → `waitUntil`). 스트리밍은 없고, 끝난 답을 보낸다. 초안을 먼저 보내면 메시지가 둘이 된다.
- 대시보드는 지금 동기 스트림이다. 비동기로 바꾸면 초안 뒤에 답을 고쳐 보여 주는 화면이 필요하다(인용 판정이 끝나면 표시를 바꾸는 흐름은 이미 있다).
- 실측은 비용이 들어 **승인 뒤 측정**으로 둔다: 정찰·보탬·Opus 호출의 실제 시간, 동시 실행 시 429, 응답 뒤 백그라운드 긴 실행.
