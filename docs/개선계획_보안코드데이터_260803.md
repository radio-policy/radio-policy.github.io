## ⑩ 보안 — anon 쓰기 개방 차단 + 대시보드 인증

### 현황 진단 (실측 완료)

대시보드는 공개 GitHub Pages + anon 키 구조이므로 **anon에 열린 권한 = 전 세계에 열린 권한**이다.
관리자 비밀번호(`ADMIN_PWD_HASH`)는 `admin_*` RPC 경유가 아닌 쓰기에는 UI 가림막일 뿐이다.

실측된 위험 상위 5건:

| 순위 | 위험 | 경로 |
|---|---|---|
| 1 | **텔레그램 봇 시스템 프롬프트 교체 (크로스 채널 인젝션)** | anon이 `app_config` upsert 가능 → `system_prompt` 행을 telegram-webhook이 그대로 읽음 |
| 2 | **뉴스 전체 무단 삭제** | `news_feed` RLS 꺼짐 — anon delete 전권 (`deleteNewsItem`이 쓰는 경로) |
| 3 | **RAG 코퍼스 주입** | `document_chunks` anon INSERT 허용 (업로드는 삭제에만 비밀번호, 삽입은 무인증) |
| 4 | **보고서 전역 프롬프트 주입** | `report_directives` anon insert — 모든 초안 시스템 프롬프트에 최우선 반영 |
| 5 | **Storage 전권** | `uploads` 버킷 정책 `uploads_anon_all` — anon 업로드·삭제 가능 |

Edge Functions 2종은 service_role이라 이 작업의 영향권 밖(정상). `telegram_subscribers` 등 3개 테이블은 이미 "정책 0개=service 전용" 모범 상태.

### 1단계 — 무파괴 잠금 (기능 손실 0, 즉시 실행 가능, 약 1~2시간)

대시보드가 **읽기만** 하는 테이블의 anon 쓰기를 전부 회수한다. 크롤러·pg_cron은 service_role이라 무영향.

1. RLS 활성 + anon select만: `law_amendments`, `assembly_bills`, `law_diffs`, `law_watch`, `law_pending`, `system_health`(이미), `kb_documents`(이미), `feedback_rules`, `daily_briefings`❋, `deleted_news`❋
   - ❋ 표시 2개는 대시보드 쓰기가 있으나(긴급도 수정 시 브리핑 동기화 / 뉴스 삭제 블록리스트) 2단계에서 authenticated로 옮길 대상 — **1단계에서는 보류하고 2단계에 포함** (안 그러면 긴급도 수정·뉴스 삭제가 깨짐).
2. **`app_config` 행 제한 정책 (최우선)**: anon 쓰기를 `key IN ('claude_key','press_keywords')` 행으로만 제한, `system_prompt` 등 나머지 행은 service 전용. → 위험 1위가 즉시 봉쇄되고 설정 화면·키워드 저장은 그대로 동작.
3. append-only 정리: `report_feedback` delete 정책 회수, `chat_logs` insert/select만 확인(삭제는 이미 admin RPC).
4. 검증: 잠근 각 테이블에 anon 키 curl로 쓰기 시도 → 401/403 확인, 대시보드 전 화면 회귀(아래 체크리스트).

### 2단계 — Supabase Auth 도입 (운영자 결정 필요 항목 있음, 반나절 + 회귀 검증)

1. Supabase Auth 이메일 로그인, 운영자 1계정 (가입 비활성 — invite only).
2. `authenticated` 역할로 이관할 연산 (실측 최종 목록):
   ```
   news_feed        : DELETE, UPDATE(locked·importance·urgency·summary·content)
   deleted_news     : INSERT
   daily_briefings  : UPDATE
   document_chunks  : INSERT  (DELETE는 admin RPC 유지)
   report_samples/style_rules/directives : 쓰기 전부
   app_config       : 잔여 anon 쓰기 2행도 authenticated로
   storage uploads  : INSERT/DELETE 정책을 authenticated로 교체
   ```
3. app.js: 로그인 UI(설정 안에 배치) + `sb.auth.signInWithPassword` 세션 유지 + 로그인 상태에 따라 운영자 버튼 노출.
4. `admin_*` RPC 7종의 `p_pwd` 해시 검증 → `auth.uid()` 검증으로 교체(비밀번호 prompt 제거).
5. `doPdfUpload` 인증 비대칭 해소 — 함수 진입 시 단일 게이트.

**운영자 결정 필요 (2단계 착수 전 확인)** — "일반 팀원이 로그인 없이 쓸 수 있어야 하는 것"의 경계:
- (a) `custom_knowledge`(추가지식): 팀원 기여 창구라고 하셨음 → anon insert/update 유지? 아니면 로그인 뒤로?
- (b) `tech_terms`: 페이지 진입 시 자동 추출이 있어 인증 뒤로 가면 방문자에게 깨짐 → anon 유지 권장, 의견 필요.
- (c) 긴급도 피드백(`news_feed.importance` update + `importance_feedback`): 팀 학습 신호 → anon 유지 권장.
- (d) `law_graph_nodes/edges`: 자문 응답마다 자동 축적 → anon insert/update 유지 권장 (delete는 이미 service 전용).

### 기능 회귀 체크리스트 (각 단계 후 전체 1회)

뉴스: 삭제·잠금·긴급도 수정·읽음·AI 요약 / 브리핑 표시 / 자문 질문(chat_logs 기록 확인) / 추가지식 등록·수정·삭제·파일 다운로드 / 업로드(추가지식·승인 흐름) / 설정: API 키 저장·승인 대기 처리 / 키워드 관리 저장 / 관계도 자동 갱신 / 구독봇 무영향 확인(/law·/ask).

## ⑫ 데이터 품질 — 선별 OCR + 품질 지표

### 실측 현황 (2026-08-02 SQL)

current 문서 중 **본문 500자 미만 = 7건뿐** (기타 5, 방송통신설비 1, 고시 1). 2,000자 미만은 38건.
→ OCR은 소품 작업이고, 실질 가치는 **품질 지표를 운영 상태 탭에 상시 노출**하는 쪽이다.

### 계획

1. **저품질 7건 개별 감정**: 각 문서를 열어 (스캔 이미지 PDF인지 / 원래 짧은 문서인지 / 파싱 실패인지) 분류 → 스캔본만 OCR 대상.
2. **Tesseract(kor) 설치 확인** → `pdftoppm`(Poppler, 설치됨) + `pytesseract`로 OCR 파이프.
3. **press_ingest OCR 폴백 훅**: 본문 추출 결과 <500자이고 첨부가 이미지형 PDF면 OCR 시도 — 이전에 실패했던 과기정통부 이미지 첨부 2건("가상융합 기금…", "국산 인공지능 반도체…")으로 실측 검증.
4. **품질 지표 — 운영 상태 탭 "KB 품질" 카드**: 본문 길이 하위 10 문서 목록 / 법령 카테고리 조문 파싱률(조문 키 인식 비율 — '충전 기술기준' 같은 미파싱 등재 자동 노출) / 임베딩 누락 수. SQL 뷰 1개 + app.js 카드 렌더.

소요 약 2~3시간(OCR 감정 결과에 따라 변동). Tesseract 미설치면 설치부터(운영자 승인 불필요한 로컬 도구).
